# V8 加载与移动端性能基线

采集时间：2026-11-15。此次只增加可复现测量脚本和 `?perf=1` 诊断探针，未减面、改轨迹、改变玻璃透明度或启用降画质。正常页面不采集性能样本。

## 已保存的数据

- `.cache/performance/v8-assets-baseline.json`：完整资产、逐网格统计、原始文件SHA256、本机Node CPU耗时。
- `.cache/performance/v8-browser-baseline.json`：本机浏览器读数与采样限制。
- `npm run profile:assets`：重新生成资产基线。FBX多次解析及Brotli默认质量的压缩统计需要一定时间，不启动HTTP服务，不访问云服务。
- `http://127.0.0.1:5173/?perf=1`：实时显示draw calls、提交三角面、RAF间隔/CPU耗时P50/P95、静止/运动样本、缓存相关资源加载信息。统计最多最近1800帧，面板每秒更新一次，仅本地显示，不上传。复制JSON可留作下一轮对比。

压缩列是本地计算的潜在传输大小，不证明部署服务器已经启用压缩。FBX二进制内部已有压缩，HTTP压缩收益小于JSON。当前运行时先下载/主线程解析完整FBX，进入回调后再fetch/JSON.parse门腔，存在串行等待，且6个原几何先加载后替换。模型目录里其他blend、ZIP、独立FBX、备用GLB不在当前页面下载链路，不能用目录总大小当首屏体积。

本机Node arm64原始FBX解析约589–675ms，门腔JSON.parse约40–45ms，生成补丁BufferGeometry约1.9ms。它们是离线CPU测量，不是浏览器主线程或手机耗时。

## 实际浏览器读数

本地macOS IAB、Vite开发服务、整体视角，CSS画布900×652，DPR2，实际缓冲1800×1304。一次缓存加载ready为867ms；资源transferSize为300字节，FBX和补丁duration分别93/81ms，属于缓存校验场景，不能宣传为移动网络冷启动时间。

- 静止531 draw calls，四窗运动534 draw calls。
- 提交三角面936,860；含透明额外pass、静态点击命中玻璃等，不等于模型唯一三角面数。
- renderer.info：502个已上传几何体、0纹理、6个program。源材质少不代表运行时材质少：代码为每个mesh重新构造标准材质，约490个槽位；共享材质可减少对象/状态管理，但单独共享不能把490个mesh变成少量draw calls。
- 最近窗口：静止829帧，RAF间隔P50/P95=8.3/9.4ms，帧CPU P95=10.3ms；四窗运动971帧，RAF间隔P50/P95=8.3/16.7ms，帧CPU P95=10.4ms。

CPU计时覆盖store/变换/controls/render提交，不是GPU时间。RAF回调时间戳与CPU计时口径不同，不能简单取倒数当真机FPS。该次未采集独立旋转场景、真实手机、热机降频或生产冷加载，不据此认定具体手机能达到某个帧率。

## 主要开销与优先级

1. **加载/首屏：大资源与主线程FBX解析。** 27.56MB原始资源、FBX→JSON串行、解析和首帧着色器/上传都在可交互前。进度100%目前只是FBX下载完成，不是整个场景就绪。
2. **绘制提交/几何：约500个碎网格、约70万面。** 当前534次draw calls和93万面提交，手机CPU/GPU压力均值得优先处理；还需真机帧分析确认各设备是CPU还是GPU先饱和。
3. **像素/透明：DPR上限2+MSAA+双面透明。** 34个玻璃/灯罩类材质组；当前Three源码中双面透明默认分正反两次绘制。灯罩和玻璃互相覆盖增加填充工作。当前没有阴影或后处理，也没有加载纹理，关闭阴影/压缩纹理不是本轮主要收益。
4. **空闲功耗：始终RAF渲染。** 静止时仍tick store、遍历记录、计算四窗轨迹及Quaternion/Vector3、更新OrbitControls、整场绘制；调试网格也在启动时准备。主循环每帧临时对象有分配开销；常规关闭页面时旧材质/替换几何/调试场景资源的释放也需梳理，防止重复进入累积。

## 建议执行方案

### 第一阶段：不改几何的运行时优化

- 手机均衡档DPR上限1.25、低档1，桌面保持至多2；同一CSS尺寸2→1.25像素量减少约61%，2→1减少75%，这不等同于帧率同比提升。低档可关闭MSAA（创建renderer时配置），减少地面网格细节；灯光简化要做观感对照。
- 按实际帧间隔自适应档位，有滞后、冷却和上下限，提供手动选择；不能仅凭屏宽判断硬件强弱。默认先尝试均衡，真机测量后决定30或60fps档。
- 按需绘制：旋转阻尼、车窗运动、选择高亮、resize、视角切换时渲染；完全静止停止GPU绘制。对话60秒到期使用独立计时/到期检查，不能随停止RAF失效；后台切回时重置时间，避免玻璃跳动或过期对话复活。
- 四窗仅在current/高亮变化时更新变换，复用向量和四元数；store只更新正在变化的窗，记录状态只在完成/替换时修改。动画推进与画质帧率分开，保证低帧率不改变总行程时间或反向响应。
- 共享等效材质，四个点击代理从常规绘制层排除但保留raycast；网格检查、碰撞证据等调试内容延迟创建/加载。释放被替换的几何与旧材质，避免释放仍在使用的共享资源。

### 第二阶段：发布专用资源与减少draw calls

- 原始FBX和门腔补丁作为源资产保存，离线烘焙出已含门腔修改的发布GLB。保留节点映射、厘米/米换算、pivot及四窗独立transform；保留固定三角玻璃。比较普通GLB与几何压缩版本的下载、解码和内存成本再选。
- 先在工作副本上索引化，只有位置/法线/UV等完整属性一致的顶点才焊接，保护硬边和接缝。再按材质合并静态、不透明零件，四窗、透明件、门腔关键边界与命中代理分开；合并后保留调试原节点映射。
- 透明单pass只做可选试验，需验证内外视角、四窗中间行程和灯罩排序，不直接全局改单面或透明度。
- 首版验收目标而非保证：将draw calls逐步降到约150以内，首屏传输相对同环境基线减少至少50%；每项都记录实际值。

### 第三阶段：局部减面与移动端LOD

优先主车壳、格栅、轮胎轮毂、灯罩和不可见内部细节，建立移动端约20–30万面候选档。首轮保留四窗、固定三角玻璃及门腔几何不变，避免破坏已验证的入门过程；如以后减玻璃，单独做曲率/轮廓对照。LOD切换不能改变玻璃轨迹、交互目标或让门腔封口，不能用隐藏玻璃或调透明度替代运动。

## 对比与验收

同一真实手机/浏览器/横竖屏/CSS画布大小/视角，记录系统版本、档位、DPR、是否充电及冷热机，避免与本机IAB数据混比。生产构建冷/热加载至少各3次：总传输量、场景ready、首个可见车模、主线程长任务、内存可用指标。场景ready当前未包含首帧绘制，后续应再加首帧时间。

每档分别记录静止10秒、持续旋转10秒、四窗同时升降/中途反向10秒，以及滑块+滚动操作记录场景；看帧间隔P50/P95与超过33ms/50ms比例、draw calls/三角面/像素数。连续使用3–5分钟检查降频。建议目标：低档稳定30fps、均衡档争取60fps，以真机P95帧间隔和触控响应验收，当前尚未测得。

功能回归必须覆盖四窗单独与批次控制、主玻璃自然入门、三角玻璃固定、0/25/50/75/100%及慢速全程、运动中反向、局部手动打断、语音/文本统一状态、60秒到期、待模型结果失效。每次资源变更重跑几何/轨迹检查并保存截图；不只看最终全开状态。
